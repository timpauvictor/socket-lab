From a cartridge idea to understanding the code

PyTorch through this experiment.

These notes explain the PyTorch parts of the experiment. The aim is to follow the code, try small examples and be honest about what the results do and don't show.

The short answer

PyTorch supplied the tensors, automatic gradients, and GPU computations used to train the adapters. Hugging Face libraries supplied the model, adapter machinery, and training loop. Most saved translation evaluations used llama.cpp, a different inference engine.

Reading the page isn't the same as understanding the code. Try the examples, change them and explain the results without looking at the answers.

01 / The stack

Which part is actually PyTorch?

PyTorch is a library for numerical computation and machine learning. Think of it as arrays of numbers plus a system that can calculate how changing those numbers changes an error. It can perform many of those operations on a GPU.

LayerIts job hereWhat it did not mean

Hugging Face DatasetsRead Wikipedia and OPUS-100; prepare dataset rows.PyTorch itself downloading or tokenizing text.

Using PyTorch through Transformers is still using a PyTorch-based system. The accurate description is adapter fine-tuning with a PyTorch-based Hugging Face stack, rather than “I implemented my own training framework.”

02 / The basic objects

A tensor is an array with a shape, type, and device.

A number is a scalar. A list of numbers is a vector. A rectangular grid is a matrix. A tensor covers these and arrays with more dimensions.

import torch
x = torch.tensor([[1.0, 2.0], [3.0, 4.0]])
print(x.shape)   # torch.Size([2, 2]): two rows, two columns
print(x.dtype)   # torch.float32
print(x.device)  # cpu
print(x * 2)    # multiply every entry by 2
print(x @ x)    # matrix multiplication, not entry-by-entry multiplication

A parameter is a tensor registered as part of a model, normally eligible for learning. An activation is an intermediate result produced while processing an input. Parameters persist between examples; activations belong to the computation on particular inputs.

Shapes in the translation trainer
NameTypical shapeMeaning
input_ids[B, 256]Integer token IDs, not floating-point words. B is examples per microbatch.
attention_mask[B, 256]1 for real input positions, 0 for padding.
labels[B, 256]Target token IDs, with -100 at positions excluded from loss.
logits[B, 256, V]One unnormalized score per possible next token. V is the vocabulary size.
lossScalarThe training error reduced to a single value for backpropagation.

The model turns integer IDs into floating-point vectors using an embedding table. A token may be a word, part of a word, or punctuation. A 256-token limit is not a 256-word limit.

Why not convert the input IDs to BF16?

They are indices into an embedding table. They need an integer type such as torch.long. BF16 is useful for floating-point model computations, not for replacing integer token IDs.

Project: tokenize_completion in translation_data.py, shared by the translation trainers. Model interface: Qwen3 documentation.

03 / The training step

Training is repeated prediction, error measurement, and adjustment.

  1. Forward pass: the model processes a batch and produces predictions.
  2. Loss: compare predictions with the training targets.
  3. Backward pass: autograd calculates gradients—how sensitive the loss is to each trainable parameter.
  4. Optimizer step: use the gradients to adjust parameters.
  5. Clear gradients: avoid unintentionally carrying them into the next update.

Autograd records differentiable operations during the forward pass. loss.backward() follows that graph backward and accumulates derivatives in parameter .grad fields. It does not update the weights. The optimizer performs the update.

# A teaching sketch, not a literal copy of Trainer's implementation.
optimizer.zero_grad(set_to_none=True)
outputs = model(**batch)
loss = outputs.loss
loss.backward()
optimizer.step()

Learning rate controls the size of the update. Too large can make training unstable; too small can make progress slow. SGD follows the gradient directly. AdamW uses running estimates of gradients and their squared values, with separate weight decay. Those running estimates are optimizer state, not model weights.

The project configures a learning rate and lets Trainer choose its optimizer implementation. It does not explicitly set optim; do not claim a particular fused optimizer ran everywhere without checking that run's library version and arguments.

Know the difference between loss and chrF.

Training minimizes next-token prediction loss. chrF is computed afterward from generated text and reference translations. The project does not backpropagate through chrF. A lower training loss does not guarantee better free-running translations.

Why clear gradients? Isn't backward supposed to replace them?

PyTorch normally accumulates gradients. That is useful for gradient accumulation, but accidental accumulation changes the update. Clear them once per intended update cycle, not between microbatches you deliberately want to combine.

Official explanations: autograd basics and optimization loop.

04 / The actual training examples

What does the model get marked on?

A translation example contains a prompt and the expected completion. During training, it sees the correct earlier tokens while learning to predict the next one. This is often called teacher forcing. At generation time it must use its own earlier predictions instead.

Prompt:     Translate the following English text to Romanian.
            English: Hello
            Romanian:
Completion: Salut

Conceptual positions:   prompt  prompt  answer  answer  EOS  padding
attention_mask:            1       1       1       1     1      0
labels:                 -100    -100    token   token  EOS   -100

The prompt is still visible. Setting its labels to -100 excludes those targets from loss; it does not remove the prompt from the input. Padding has a different role: the attention mask marks padded input positions as unavailable for normal attention.

A third mask—the model's causal attention mask—prevents looking ahead at future tokens. That is why including the answer tokens during training is not permission for a position to look at its own future target.

The one-token shift

The prediction at position 0 is compared with the target at position 1, and so on. The logit immediately before the first answer token predicts that answer token. Transformers handles this shift inside the causal-language-model loss. The project supplies unshifted labels; manually shifting them again would be wrong.

Cross-entropy takes raw logits and target IDs; do not apply softmax first when using torch.nn.functional.cross_entropy. The loss's ignore_index=-100 excludes the masked targets. -100 is not a token to generate.

Language adapters

train_box.py uses full blocks of Wikipedia tokens, normally 256 long. Labels copy the input IDs. There is no completion-only label mask or padding in these full blocks; the causal model still performs the next-token shift.

Translation adapters

train_lora.py and train_task.py build both translation directions, pad to 256 positions, and mask prompt and padding labels. A collator stacks rows into PyTorch tensors.

The end-of-text change

With --eos_stop, the monolith script reserves one position and appends a supervised end-of-sequence token, or EOS. It is a target that teaches a possible stopping point. Merely using the EOS token as padding does not teach stopping when those padding labels are ignored.

The later adapter repeated text less often, but extra training and the target-format change happened together. That does not isolate which change caused the improvement.

A real boundary bug: a long prompt could fill the token budget and leave no completion tokens to train on. The current scripts reject that condition. A completely ignored target batch has no useful supervised learning signal; a reduced loss can also become invalid. The regression tests use synthetic tokenizers, not a full corpus audit.

Project: token-label regression tests. Library behavior: CrossEntropyLoss, Transformers ForCausalLMLoss source.

05 / The cartridge mechanism

LoRA learns a small adjustment, not a new base model.

A normal linear layer computes y = W x, ignoring the bias for this explanation. LoRA keeps W fixed and learns two smaller matrices, A and B:

y = W x + scale × B A x

W: [output_features, input_features]  — frozen base weights
A: [rank, input_features]             — trainable
B: [output_features, rank]            — trainable
scale = lora_alpha / rank            — ordinary LoRA scaling

Rank is the size of the narrow intermediate dimension. For a hypothetical 1,024 × 1,024 layer, W contains 1,048,576 numbers. Rank-16 A and B contain 32,768 numbers together. That example is arithmetic, not a claim about a specific Qwen layer's dimensions.

The project targets q_proj, k_proj, v_proj, and o_proj: attention's query, key, value, and output projections. In brief, queries and keys decide which earlier information to attend to; values carry that information; the output projection combines it. PEFT inserts the LoRA branches into those existing layers.

The full language adapters use rank 16. The task and monolithic adapters use rank 32. The training scripts set lora_alpha = 2 × rank and lora_dropout = 0.05. Dropout randomly drops some values during training as regularization; evaluation mode disables it.

How freezing works

requires_grad=False excludes a parameter from gradient accumulation. PEFT configures trainable adapter parameters for a fresh adapter. In the project's reload paths, a loop explicitly enables gradients on parameters whose names contain lora_, then verifies that some were found.

# Actual pattern from the adapter reload path.
for pname, param in model.named_parameters():
    if "lora_" in pname:
        param.requires_grad = True

That name-based rule is specific to the current adapter layout, not a universal freezing API. Inspect trainable names and counts instead of assuming that a successfully loaded adapter is trainable.

Frozen does not mean “put the whole model in no_grad.”

Gradients may need to flow through computations involving frozen layers to reach trainable adapter parameters. Disabling gradient recording for the entire forward pass would prevent adapter learning. LoRA reduces trainable weights and their optimizer state, but the base model still consumes memory and computation.

Why the separate-adapter comparison is tricky

The task trainer merges language adapters into a fresh base, then trains the task adapter over that base. Its historical PEFT linear merge combines the A and B factors, with weighting and scaling. Combining factors is not generally the same as adding complete adapter updates.

# Simplified algebra showing the issue, with scaling omitted:
(B1 + B2)(A1 + A2) = B1A1 + B1A2 + B2A1 + B2A2
B1A1 + B2A2       = sum of the separate updates
# The first expression has cross terms.

The llama.cpp comparisons stack adapter updates differently. This mismatch limits conclusions about whether independent cartridges are useful. It is not evidence that PyTorch's gradients are incorrect, and LoRA itself does not guarantee no forgetting.

Project: train_task.py. Background: PEFT LoRA guide, PEFT merge algorithms.

06 / The loop you delegated

Trainer did the repetitive work. You still need to understand it.

Trainer builds the training data loader, runs batches through the model, requests gradients, updates weights, manages the learning-rate schedule, and writes checkpoints. The repository did not implement its own production calls to loss.backward() or optimizer.step().

A Dataset supplies examples. A DataLoader groups and iterates over them. A collator turns several examples into one batch. Here, default_data_collator stacks already prepared rows. It does not add the completion mask or pad arbitrary lengths for us.

Read these settings in the source, not as unexplained magic
SettingMeaning here
per_device_train_batch_size=8Default of eight examples in one microbatch on one device. CLI arguments can override it.
gradient_accumulation_steps=4Combine gradients from four microbatches before an optimizer update: nominally 32 examples on one device.
num_train_epochs=2A requested two passes over the prepared data unless a positive step limit takes precedence.
max_stepsOptimizer-update limit, not number of individual examples. Used for short smoke tests and the tune-up.
warmup_ratio=0.05, cosine scheduleIncrease the learning rate during an initial warmup, then decrease it along a cosine schedule.

save_steps=500, save_total_limit=2Periodic checkpoints with a bounded retained count. Final adapter saving is a separate call.

With accumulation, the important idea is to delay the optimizer update while combining gradients with the correct loss normalization. Do not blindly divide every framework loss by four: Trainer already handles accumulation, and valid-token counts matter for variable-length examples.

With D devices, the usual nominal effective batch is microbatch × accumulation × D. That is general knowledge, not a claim that this project ran multi-GPU data parallelism. A final partial batch can also be smaller.

A missing validation distinction: these training scripts pass a training dataset, not a held-out evaluation dataset to Trainer. There is no configured early stopping here. Final training loss is not a held-out translation score; the saved translation evaluations are a separate stage.

Project: the TrainingArguments and Trainer calls in train_lora.py. Reference: Trainer 4.57.1; exact defaults depend on the installed version.

07 / Memory is more than weights

Device, precision, and memory are separate choices.

A tensor has a device. tensor.to("cuda") returns a tensor on a CUDA GPU; assign or use the returned value. model.to("cuda") moves a module's parameters and buffers. Inputs and the operations consuming them must be on compatible devices.

The training scripts load weights with torch_dtype=torch.bfloat16 and request bf16=True in Trainer. BF16 uses 16 bits per value, with less precision than FP32 but a similar exponent range. The whole computation is not necessarily BF16: libraries may retain or upcast certain tensors and operations, including loss calculations.

BF16 and FP16 are different 16-bit formats. BF16 usually does not need the gradient scaling commonly used with FP16. Neither format guarantees stability or a speedup on every device. The project scripts target suitable GPUs; do not expect their BF16 training setup to be a portable CPU tutorial.

What uses memory?

  • Base and adapter weights.
  • Activations retained for backward.
  • Gradients and optimizer state.
  • Temporary buffers and allocator reservations.
  • During generation, the attention key/value cache.

When memory runs out

  • Reduce the microbatch first.
  • Consider shorter sequences.
  • Use accumulation if a larger effective batch is needed.
  • Check whether old models or graphs are still referenced.
  • Measure rather than assuming cache clearing fixes it.

torch.cuda.empty_cache(), called between task-pair cycles, releases unused cached allocations. It cannot free live tensors. Even del model does not free an object if something else—such as the current Trainer—still holds it. This guide explains that limitation; it does not claim the existing cleanup is optimal.

Q8_0 is different again. It is a quantized model representation used for llama.cpp inference. Loading BF16 weights for PyTorch training and evaluating a Q8_0 GGUF model are different execution paths. This project did not thereby implement QLoRA training.

Activation checkpointing trades recomputation for memory and is useful background knowledge, but these training scripts do not explicitly enable it. Do not confuse it with saving a training checkpoint to disk.

Project: task cleanup, CUDA availability/version checks. Official behavior: empty_cache.

08 / Using the trained model

eval() and inference_mode() solve different problems.

# Pattern used by the project's PyTorch probes.
model.eval()
with torch.inference_mode():
    enc = tok(prompt, return_tensors="pt").to("cuda")
    out = model.generate(**enc, max_new_tokens=128, do_sample=False)
ControlWhat changesWhat does not
model.eval()Mode-dependent layers such as dropout switch to evaluation behavior.It does not turn off autograd or freeze parameters.
torch.no_grad()Disables recording operations for backward within the context.It does not put dropout into evaluation mode.
torch.inference_mode()Disables gradient recording and additional tracking overhead for inference.It does not call eval(); tensors created there have restrictions on later autograd use.
requires_grad=FalseControls whether a parameter participates as a gradient-accumulating leaf.It does not switch model mode.

generate() repeatedly runs the model, selects another token, and continues until a stop condition. do_sample=False selects greedy decoding in these unconfigured-beam probe calls. It does not prove bit-for-bit reproducibility across hardware or software versions.

Decoder-only generation returns the prompt tokens followed by generated tokens. The probes slice off enc["input_ids"].shape[1] before decoding. The legacy batched evaluator uses left padding so shorter prompts end at the same right-hand position in the batch.

Where this actually appears

  • probe_terminate.py: six prompts, GPU model loading, greedy generation, generated-token and repetition diagnostics.
  • Modal monolith wrapper and other training wrappers: small post-training probes using PyTorch.
  • eval_translate.py: legacy PyTorch evaluator. It exists, but do not describe it as the engine behind all the banked chrF runs.
  • eval_llama.py, eval_offline.py, eval_pivot.py, and eval_scratchpad.py: request text from a llama.cpp server. They do not run a PyTorch forward pass themselves.

chrF and the repeated-word diagnostic operate on text. Neither requires gradients. Repetition is not itself proof that a model failed to emit EOS: older evaluation records do not include the finish reasons needed to settle that.

09 / What was actually saved?

An adapter file is not a complete training checkpoint.

In plain PyTorch, a model's state_dict() maps parameter and persistent-buffer names to tensors. Saving model state is different from saving the Python model definition or a complete training process.

Here, model.save_pretrained(output) on a PEFT model saves adapter weights and configuration, not another full copy of Qwen. Reloading needs a compatible base model and adapter configuration. The repository contains metadata and links; it does not contain all the model weights.

Saved stateWhy it matters
Model / adapter weightsWhich parameters have been learned so far.
Optimizer stateFor example, Adam's running estimates; restarting them changes training.
Scheduler and step countWhere the learning-rate schedule is and how many updates remain.
Random-number and data progress stateWhich examples, order, and random operations come next.

The monolith script's --resume_from restores adapter weights and reads the previous step count to estimate remaining updates. It deliberately starts a fresh optimizer and scheduler, and restarts data order. That is continuing from learned weights, not an exact continuation of the interrupted process.

--tune_from is also a weight reload with fresh optimizer/scheduler, but uses an explicit step cap instead of subtracting prior steps. The EOS tune-up follows this pattern. The task script separately exposes Trainer checkpoint resume; it also depends on the expected task-adapter output directory being present. A full recovery test was not established by the earlier review.

Seeds help, but a seed alone is not reproducibility. The project seeds Python sampling and passes a seed to TrainingArguments. That does not prove every model-initialization, GPU kernel, version, and data-order choice was identical. Be especially careful about initialization that occurs before a framework sets its random seed.

Project: resume/tune branches, task resume branch, EOS completion record.

10 / Other PyTorch use

Compilation and file conversion are not training methods.

torch.compile

torch.compile(model) tries to capture and optimize regions of model computation. The scripts use the default Inductor backend when --compile is enabled. Compilation has startup cost; unsupported operations can cause graph breaks or failures. It is not a promise of faster end-to-end runs.

The journal reports compiled task runs and two short comparisons: plain/compiled took 37/109 seconds on one host and 80/214 seconds on another, with similar losses. Those short totals were slower with compilation. They don't show a speedup. A longer job might spread the startup cost over more work, but that was not shown by these short checks.

The current training scripts make compilation optional. Vast run scripts enable it for task and monolith runs; the EOS tune-up scripts deliberately omit it. A particularly useful debugging lesson was Trainer removing dataset columns after compilation obscured the model's forward signature.

Adapter and model conversion

The bundled GGUF conversion code also uses PyTorch. It loads weight tensors, moves or loads them onto the CPU, changes dtypes, reshapes and permutes dimensions, joins or splits tensors, and exports data into the format llama.cpp expects. That is numerical file transformation, not another learning step.

  • reshape changes shape while retaining logical element order; permute reorders dimensions.
  • view has memory-layout requirements; a permuted tensor may need contiguous() before certain views.
  • cat joins an existing dimension; stack creates a new dimension.
  • torch.load(..., map_location="cpu", weights_only=True) limits weight loading and avoids requiring the original GPU. It is not permission to load arbitrary untrusted files.
  • Safetensors loading is provided by the safetensors library. The result is still tensors used by the conversion code.
Advanced appendix: do I need to claim I wrote custom tensor machinery?

No. The bundled converter includes LoraTorchTensor, LazyTorchTensor, __torch_function__ dispatch, delayed materialization, and low-bit packing routines for multiple model formats. They are supporting conversion infrastructure. Recognize their role; do not present every supported format or operation as something this experiment exercised or as code you designed.

Project: compile smoke runner, historical journal, LoRA converter, conversion base and lazy tensors, bundled lazy-array support. Official: torch.compile.

12 / Learn by changing something

Three small CPU labs. No model downloads.

Run each block separately with Python in an environment where PyTorch is already installed. If you need to install it, use the official installation selector for your platform and an isolated environment. These examples deliberately use CPU tensors, not the project's GPU training launchers.

Validation: these three exact blocks were run on CPU with PyTorch 2.12.0+cpu. The expected properties below are assertions in the examples. Small floating-point differences across versions are normal.

Lab A · Watch one weight learn

Before running: with weight 2 and input 3, the prediction is 6. The target is 9. Which direction should the weight move?

import torch

weight = torch.nn.Parameter(torch.tensor(2.0))
optimizer = torch.optim.SGD([weight], lr=0.05)
x, target = torch.tensor(3.0), torch.tensor(9.0)
initial_loss = ((weight * x - target) ** 2).item()

for step in range(12):
    optimizer.zero_grad(set_to_none=True)
    loss = (weight * x - target) ** 2
    loss.backward()
    if step == 0:
        print("first gradient:", weight.grad.item())
        torch.testing.assert_close(weight.grad, torch.tensor(-18.0))
    optimizer.step()

final_loss = ((weight * x - target) ** 2).item()
assert final_loss < initial_loss
print("weight:", round(weight.item(), 4))
print("loss:", initial_loss, "->", final_loss)
Expected result and a useful variation

The first gradient is −18; subtracting a positive learning rate times that negative gradient increases the weight. It approaches 3 and the loss falls from 9 toward zero. Try learning rate 0.2: this simple problem becomes unstable. Explain why a bigger step is not automatically better.

Lab B · Train a tiny LoRA-like add-on

This is a teaching model, not Qwen or PEFT. It makes the frozen base, trainable matrices, DataLoader, and training loop visible. It uses mean-squared error because its targets are vectors, not token classes.

import torch
from torch import nn
from torch.utils.data import DataLoader, TensorDataset

torch.manual_seed(7)

class TinyAdapter(nn.Module):
    def __init__(self):
        super().__init__()
        self.base = nn.Linear(4, 3, bias=False)
        self.base.requires_grad_(False)
        self.a = nn.Linear(4, 2, bias=False)
        self.b = nn.Linear(2, 3, bias=False)
        nn.init.zeros_(self.b.weight)

    def forward(self, x):
        return self.base(x) + 2.0 * self.b(self.a(x))

model = TinyAdapter()
x = torch.randn(24, 4)
y = torch.zeros(24, 3)
loader = DataLoader(TensorDataset(x, y), batch_size=6, shuffle=True)
optimizer = torch.optim.SGD(
    [p for p in model.parameters() if p.requires_grad], lr=0.05
)
base_before = model.base.weight.detach().clone()
b_before = model.b.weight.detach().clone()
with torch.no_grad():
    initial_loss = nn.functional.mse_loss(model(x), y).item()

model.train()
for epoch in range(40):
    for batch_x, batch_y in loader:
        optimizer.zero_grad(set_to_none=True)
        loss = nn.functional.mse_loss(model(batch_x), batch_y)
        loss.backward()
        optimizer.step()

model.eval()
with torch.inference_mode():
    final_loss = nn.functional.mse_loss(model(x), y).item()

assert model.base.weight.grad is None
assert torch.equal(base_before, model.base.weight)
assert not torch.equal(b_before, model.b.weight)
assert final_loss < initial_loss
print("base unchanged; adapter changed")
print("loss:", initial_loss, "->", final_loss)
What should I be able to explain?

Input is [6, 4] for each full batch; A produces [6, 2]; B produces [6, 3]; the base also produces [6, 3], so addition is valid. Only adapter parameters enter the optimizer. The frozen base still contributes to predictions. detach().clone() makes an independent snapshot for the comparison.

Because B starts at zero, the add-on initially contributes zero. A can have a zero gradient on the first backward pass because the signal to A passes through B. That does not mean the whole adapter is broken. This toy intentionally omits dropout, tokenization, attention, and checkpointing.

Lab C · See exactly which tokens contribute to loss

The token IDs below are invented. This isolates the loss rule; it does not load a tokenizer. We manually shift here to teach what the model normally does internally.

import torch
from torch.nn import functional as F

torch.manual_seed(3)
# Positions: prompt, prompt, answer, answer, EOS, padding
labels = torch.tensor([[-100, -100, 31, 32, 2, -100]])
logits = torch.randn(1, 6, 40, requires_grad=True)

shift_logits = logits[:, :-1, :].contiguous()
shift_labels = labels[:, 1:].contiguous()
loss = F.cross_entropy(
    shift_logits.view(-1, 40),
    shift_labels.view(-1),
    ignore_index=-100,
)
loss.backward()

active = logits.grad.abs().sum(dim=-1).squeeze(0) > 0
assert active.tolist() == [False, True, True, True, False, False]
assert (shift_labels != -100).sum().item() == 3
print("logit positions with gradient:", active.nonzero().flatten().tolist())
print("three targets: first answer, second answer, EOS")
Why does the final prompt position get a gradient?

Its logit predicts the first answer token. The loss masks target positions, not every computation associated with a prompt token. This is the distinction between “don't grade the prompt as a target” and “don't use the prompt.” Try changing the EOS label to −100 and predict the new active positions before running it.

13 / Troubleshooting

Practice saying what you would inspect first.

“The loss has no grad_fn” or backward says it does not require grad.

Check whether trainable parameters exist, whether the forward pass was inside no_grad/inference_mode, and whether loss was detached or converted to a Python number before backward. In this project, inspect the adapter reload and trainable-parameter count. Do not randomly unfreeze every base weight to make the error disappear.

The GPU runs out of memory halfway through.

Inspect batch and sequence lengths, live tensor references, and whether you store whole loss tensors instead of detached scalar values. Compare allocated versus reserved memory. Reduce the microbatch if needed; accumulation does not remove the need to fit one microbatch. empty_cache cannot free tensors still referenced by a Trainer.

“Expected all tensors to be on the same device.”

Print model/input devices. Move the inputs using the returned value from .to(device). The small probes explicitly move both model and tokenized input to CUDA; Trainer handles placement in the training path. Do not blindly move a deliberately sharded model to one GPU.

“mat1 and mat2 shapes cannot be multiplied.”

Write down the last input dimension and the layer's input feature count. For a linear layer, input [..., in_features] meets weights [out_features, in_features]. Transposing or reshaping without understanding the dimensions can hide the mistake rather than fix it.

Training loss decreases, but generation repeats.

Training uses correct earlier tokens; generation uses its own. Inspect target formatting, EOS supervision, stopping settings, data quality, and generated samples. A low teacher-forced loss does not certify good generation. The project found less repetition after a tune-up, but did not isolate its cause.

Training behaves differently after a restart.

Ask what was restored: weights only, or optimizer, scheduler, random state, and data progress too? The monolith's manual resume restarts several of these. A saved step number alone cannot restore them.

The compiled model fails inside Trainer before learning.

Inspect the input batch keys and the model signature seen by Trainer. The repository records a column-removal problem and keeps prepared columns with remove_unused_columns=False. That is a fix for this interface mismatch, not a universal way to resolve compiler errors.

Questions about the code.

A short account of the experiment

I explored whether small adapters could act like cartridges for an existing language model. I used a PyTorch-based Transformers and PEFT stack to train adapters for translation. Trainer handled the optimization loop; the project code prepared the examples, controlled which labels contributed to loss, and configured training. The single adapter improved some recorded translation scores, but separate cartridges did not demonstrate an advantage.

The runs show what the experiment did. They don't show that I wrote the libraries or understand every part of them.

The short version

A translation-adapter experiment using PyTorch, Hugging Face Transformers and PEFT. It compares saved translations with the base model using chrF.

This wasn't a production deployment, a distributed-training project or a test of custom GPU kernels. It didn't prove that the cartridge idea works.

Answer these before opening the explanations

1. What did PyTorch do that plain Python lists did not?

Efficient tensor operations, hardware-backed computation, model/parameter abstractions, and automatic differentiation. The surrounding Python code arranged data and called these systems.

2. What is the difference between backward and optimizer.step?

Backward computes and accumulates gradients. The optimizer uses those gradients and any optimizer state to update parameters. Neither operation should be confused with measuring chrF.

3. Why use LoRA instead of updating all the weights?

It trains and stores a smaller set of parameters, reducing adapter storage and optimizer-state needs. It still needs the base model and forward/backward computation; it does not automatically preserve every capability or make independent adapters compose well.

4. What is a batch, epoch, and step in this project?

A microbatch is a group processed in one forward/backward pass. An epoch is one pass over the prepared dataset. An optimizer step updates the weights, potentially after several microbatches. With defaults 8 and 4 on one device, a full update nominally combines 32 examples.

5. Why are labels different from input_ids?

The prompt and padding still occupy input positions, but their labels are −100 to exclude them from the supervised target loss. The answer tokens—and EOS when enabled—are the graded targets. Transformers performs the next-token shift.

6. Why do you need both eval() and inference_mode()?

One changes layer behavior such as dropout; the other disables gradient recording and related tracking. They are independent.

7. Did all the saved evaluations use PyTorch?

No. PyTorch was used for training and small generation probes, and there is a legacy PyTorch evaluator. The main banked comparisons requested generations from llama.cpp and scored the text separately.

8. What mistake or limitation can you explain concretely?

Choose one you understand: all-masked completion labels at the token limit; weights-only resume not restoring optimizer state; or the mismatch between combining LoRA factors during training and stacking updates during evaluation. Explain the failure, not just the fix name.

9. How would you check that an adapter actually learned?

Verify trainable parameters and nonzero useful gradients, compare adapter weights before/after, inspect loss and generated examples, and evaluate held-out outputs against a baseline. The toy lab checks parameter changes; it is not a translation-quality test.

10. Why can a fixed random seed still give different results?

Versions, hardware, nondeterministic operations, initialization timing, and data ordering can differ. An exact restart also needs more than model weights. The recorded environment is not fully pinned.

11. Can you write a small training loop without Trainer?

You should be able to recreate Lab B: dataset/data loader, model, loss, optimizer, clear gradients, forward, backward, step, then eval with gradients disabled. If you cannot yet, say your experience is with Trainer and keep practicing this part.
